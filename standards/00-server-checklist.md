# 00 服务器企业化验收清单

> 一台服务器"可管理、可追溯、可恢复、可观测"的完整标尺。
> 摸底时逐项核对,验收时逐项打勾。每台机器的核对结果记入 inventory 条目的 notes。
>
> 优先级:**P0** = 不达标就是事故隐患,限期整改;**P1** = 应该有,排期整改;**P2** = 加分项,有余力再做。

## 1. 资产与标识

- [ ] P0 主机名符合 `<环境>-<角色>-<序号>` 规范,cloud 控制台名称一致
- [ ] P0 已登记 `inventory/servers.yaml`(IP、云、区域、系统、角色、跑什么)
- [ ] P1 云资源打了统一标签(env / role / project / owner)
- [ ] P1 明确这台机器的用途和依赖它的业务(说不清用途的机器 = 隐患)
- [ ] P2 实例到期时间、计费方式已确认并记录(防止突然欠费停机)

## 2. 系统基线

- [ ] P0 时区 UTC + NTP 同步正常(`timedatectl` 确认 synchronized: yes)
- [ ] P0 数据、日志、应用三分离(/data、/var/log/<服务>、/opt/compose 或 /opt/apps)
- [ ] P1 有独立数据盘的机器,/data 单独挂载;没有的在台账注明
- [ ] P1 journald 留存有上限(SystemMaxUse=500M),不无限膨胀
- [ ] P1 内核参数基线已应用(/etc/sysctl.d/99-ops-baseline.conf)
- [ ] P2 swap 策略明确(有或没有都是决策,不是默认值)

## 3. SSH 与账号

- [ ] P0 禁止密码登录(PasswordAuthentication no)
- [ ] P0 禁止 root 直接登录(PermitRootLogin no)——存量 root 登录先记录,排期整改
- [ ] P0 authorized_keys 里没有来路不明的公钥
- [ ] P1 个人账号 + sudo,而非共用 root
- [ ] P1 sudo 白名单(排障账号只放行只读命令)
- [ ] P2 SSH 端口限制来源 IP(安全组层面)

## 4. 防火墙与网络暴露

- [ ] P0 防火墙开启,默认拒绝入站(ufw / firewalld)
- [ ] P0 每个对公网开放的端口都能说出"为什么开、给谁用",并登记在台账
- [ ] P0 数据库/缓存/内部服务(3306/6379/9100 等)不暴露公网,只允许内网访问
- [ ] P0 安全组无 0.0.0.0/0 的全端口放行
- [ ] P1 fail2ban 运行中,SSH 爆破有防护
- [ ] P2 不用的端口/历史遗留规则已清理

## 5. 服务部署

- [ ] P0 所有服务位置可预测(/opt/compose/<项目>/ 或 /opt/apps/<服务>/,无散落 /root、/home 的服务)
- [ ] P0 所有服务开机自启(restart: unless-stopped 或 systemctl enabled)
- [ ] P0 镜像用固定版本 tag,禁止 latest
- [ ] P1 每个服务有健康检查(compose healthcheck 或探活端点)
- [ ] P1 容器以非 root 用户运行(有 USER 指令)
- [ ] P1 服务用专属低权限系统账号,不用 root 跑
- [ ] P2 资源限制(容器 memory limit,防止一个服务吃垮整机)

## 6. 凭证与配置管理

- [ ] P0 无明文密码/AccessKey 硬编码在脚本、compose、crontab 里
- [ ] P0 凭证统一放 secrets.env / .env(已在 .gitignore 排除)
- [ ] P1 配置文件进 Git(可追溯谁改了什么),凭证与配置分离
- [ ] P2 凭证有轮换记录(什么时候换过、下次何时换)

## 7. 日志

- [ ] P0 应用日志落 /var/log/<服务名>/,不散落在应用目录里
- [ ] P0 日志有轮转(logrotate:每日、保留 14 天、压缩),不会撑爆磁盘
- [ ] P0 容器日志有大小限制(max-size/max-file)
- [ ] P1 promtail 已部署,日志进 Loki 可集中查询
- [ ] P2 关键服务的错误日志有告警(Loki ruler 或 Grafana alert)

## 8. 监控告警

- [ ] P0 node_exporter 运行中,Prometheus 已采集这台机器
- [ ] P0 基础告警覆盖:宕机、磁盘 >85%、内存 >90%
- [ ] P1 关键服务有存活探测(HTTP 探活或进程监控)
- [ ] P1 公网域名的 SSL 证书过期监控
- [ ] P1 数据库有专属 exporter(mysqld_exporter / redis_exporter)
- [ ] P2 Grafana 有这台机器的 Dashboard 视图

## 9. 备份与恢复

- [ ] P0 识别了这台机器上"丢了会出事"的数据,每一份都有备份方案
- [ ] P0 数据库用逻辑备份(mysqldump / RDB),不是只拷文件目录
- [ ] P0 备份存到异云对象存储(阿里云机器 → COS,腾讯云机器 → OSS)
- [ ] P1 备份脚本有日志和失败告警(静默失败的备份 = 没有备份)
- [ ] P1 保留策略执行中(日备 7 份、周备 4 份)
- [ ] P1 做过至少一次恢复演练,有记录
- [ ] P2 明确这台机器挂了的恢复步骤(RTO/RPO 写进 runbook)

## 10. 补丁与更新

- [ ] P0 自动安全更新开启(unattended-upgrades / dnf-automatic)
- [ ] P1 系统版本在生命周期内(不跑 EOL 的系统)
- [ ] P2 内核更新有季度计划,重启窗口明确

## 11. 文档与可追溯

- [ ] P0 /opt/ops 已克隆且与远程同步
- [ ] P0 这台机器的所有服务、端口都在台账里,台账与实际一致
- [ ] P1 变更走 Git(改了配置有 commit 记录,能回答"这是谁什么时候为什么改的")
- [ ] P1 crontab 里的每一行都能说清楚是干什么的,脚本在 /opt/ops/scripts/
- [ ] P2 关键服务有对应 runbook(挂了怎么排查、怎么恢复)

## 12. 资源与成本

- [ ] P1 磁盘/内存/CPU 水位健康(磁盘 <80%,不长期内存打满)
- [ ] P1 实例规格与实际负载匹配(长期 <10% 利用率考虑降配,长期 >80% 考虑升配)
- [ ] P2 无僵尸资源:未挂载的云盘、闲置 EIP、不用的快照/镜像
- [ ] P2 云账单按月过一眼,异常波动能解释

---

## 使用方式

1. **摸底**:让 Agent 对照本清单逐项检查,输出「达标 / 不达标 / 不适用」三态清单
2. **评分**:P0 全达标 = 合格;P0+P1 全达标 = 良好;全达标 = 企业化
3. **整改**:不达标项按 P0 → P1 → P2 排期,每项整改走 standards/05 变更流程
4. **验收**:新机器上线前过一遍本清单,P0 不全过不准承载生产服务
